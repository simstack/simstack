# Minimal workflow changes for the API-only Runner

Runner uses Server URL and a resource token. MongoDB is owned by Server. Remove Mongo clients, connection strings, `[parameters.db]` and database initialization from workflow repositories and resource environments. Do not copy DB settings into Docker, Apptainer or Slurm jobs.

Ordinary `context.db.find`, `find_one`, `save`, references and model hooks retain their interfaces and use the document API. `context.db` is a compatibility name for that API client: it exposes no Mongo client or collections in Runner mode. Task claims, guarded state changes and parent links use explicit Server operations. No Mongo query language, BSON values or database sessions cross this boundary.

Import domain classes from `simstack.models` (`Model`, `EmbeddedModel`, `Field`, `Reference`, `ObjectId`) instead of `odmantic` or `bson`. The document classes are Pydantic models; they contain no database driver or engine. Identity remains a 24-character string. Existing class-field comparisons describe neutral API criteria. Code that opens collections, constructs Mongo operators or calls an ODMantic engine must use the document facade or a dedicated Server operation instead. Update workflow dependency declarations and lockfiles so the old ODMantic dependency is not installed transitively.

Registration belongs to Server. Importing a repository produces its model/node catalogue using an isolated in-memory collector and the recursive table builders; no Runner is required and no Mongo mock is used. Runner constructs calculation results in memory and sends them through the API; Server performs the actual database writes. Hooks which prepare live workflow objects remain beside those objects and use the same API facade. Server-specific validation and catalogue methods can require temporary access to the pinned Python source, not just its JSON Schema.

The document adapter tracks the loaded snapshot and sends changed fields, including changes inside mutable containers. A loaded model's full Pydantic dump is not a write set. Preserve this behavior when extending the API so a task status update cannot overwrite a simultaneous edit from the UI. Database conversion, collection access and atomic database updates belong exclusively to the Server repository.

Keep workflow decorators, argument/result models, nested calls, parameters, resource assignments, container settings and error/logging conventions. `FileStack` call signatures remain; `in_memory` is accepted for compatibility but file bytes are never persisted in MongoDB. String/file constructors stage data locally, publication stores S3 metadata, and execution prefers a valid local copy before requesting a signed download URL.

Ensure the repository declares the intended Python version, locked dependencies, recursive Git submodules and optional dependencies in the existing per-resource configuration. Workflow environments use the Core version installed with Runner after resolving workflow dependencies; an older workflow dependency does not replace that platform package. System binaries, licensed programs, HPC modules and resource startup commands remain machine configuration.

Test at least a native workflow, a nested/subworkflow call, a model save/load with references and a file-producing workflow; also test each Docker/Apptainer/Slurm path used by the repository. For versioning, queue a v1 task, publish v2, and verify the queued task and its children retain v1 while new submissions use v2. The UI does not add historical-version selection for new tasks.

Connect a repository in the UI with its SSH or HTTPS clone URL and selected branch. Private SSH access uses one Ed25519 key per SimStack user: add the public key to the Git service, inspect and explicitly confirm the actual host's fingerprints, then enroll each Runner using its short-lived, one-use installer token over HTTPS. Enrollment installs the same user's private key locally with permissions `0600`; an ordinary Runner API token cannot download it again. Unknown or changed host keys are rejected. Submodules and private Git dependencies need access and trusted host keys for their own hosts as well.

Server loads pinned Git revisions using the existing recursive model/node table builders in isolated temporary runtimes, with SSH credentials available to Git and `uv sync --locked` but excluded from discovery. It retains repository identity, branch, commit/submodule/tag metadata and the catalogue, then removes its temporary source checkout. Later schema, validation, table and artifact operations use the same Git access to restore the required revision temporarily. Removing a commit or revoking access can prevent restoring a missing checkout; Server does not retain persistent source snapshots.

Runner receives version preparation commands through the API control poll and obtains the pinned source directly from Git. It verifies the commit, recursive submodules and tags, runs `uv sync --locked` with its resource extras, and retains a separate source/runtime cache for each revision and extras profile. Server admits tasks for that resource only after successful preparation is acknowledged as ready. Preparation waits while persisted tasks show that the resource is busy; existing tasks and children continue using their original versions. Startup reconciles locally verified runtimes with Server before task admission, so a cold or reinstalled Runner prepares missing versions through the same control path.
